## 1. כתיבת Skills ברמה מקצועית

### מבנה
```text
weekly-report/
├── SKILL.md            חובה: שם, תיאור והוראות
├── reference/          מסמכי עזר, נטענים לפי הצורך
│   ├── template.md
│   └── examples.md
└── scripts/            סקריפטים שרצים ולא נטענים להקשר
```

**ארזו כ-ZIP כשתיקיית ה-Skill בשורש.** העלאה: Customize > Skills > **+** > Create skill > Upload a skill.

### כללי שדות
| שדה | כלל |
|---|---|
| `name` | עד 64 תווים, אותיות קטנות באנגלית, ספרות ומקפים. בלי המילים `claude` או `anthropic` |
| `description` | עד 1,024 תווים, **בגוף שלישי**, מה עושה **ומתי** להשתמש בו |

**תיאור חלש:** `Helps with documents`
**תיאור טוב:** `Prepares the weekly management report from team data and the latest sheet. Use when the user asks for a weekly report, a weekly summary, or a status update for management.`

> תיאורים בגוף ראשון ("אני יכול לעזור…") פוגעים בגילוי ה-Skill, כי התיאור מוזרק להנחיית המערכת.

**שם מומלץ:** פועל בצורת gerund (`preparing-weekly-reports`) או שם עצם ברור. הימנעו מ-`helper`, `utils`, `documents`.

### שבעה עקרונות כתיבה
1. **קצר.** Claude כבר חכם. לכל פסקה שאלו: "האם הוא באמת צריך להסבר הזה, והאם הפסקה שווה את המקום שהיא תופסת בהקשר?"
2. **גוף הקובץ עד כ-500 שורות.** מעבר לכך, העבירו חומר לקבצי עזר.
3. **רמת חופש לפי הסיכון:** משימה גמישה (סקירת קוד) מקבלת הנחיות כלליות. משימה שביר (מיגרציה) מקבלת סקריפט מדויק.
4. **דוגמת פלט מושלם.** דוגמאות מכוונות טוב יותר מהסברים.
5. **קבצי עזר עד רמה אחת מ-`SKILL.md`.** הפניות מקוננות גורמות לקריאה חלקית. לקבצים מעל 100 שורות, הוסיפו תוכן עניינים.
6. **מונחים עקביים.** מונח אחד לכל מושג לאורך כל הקובץ.
7. **בלי מידע שיתיישן.** חומר ישן בסעיף "דפוסים ישנים".

### צ'קליסט שלבי עבודה (לתהליכים מורכבים)
כללו ב-Skill רשימה שאפשר להעתיק לתשובה ולסמן:
```text
דוח שבועי:
- [ ] קרא את הגיליון העדכני
- [ ] זהה 3 הישגים ו-3 סיכונים
- [ ] בדוק כל מספר מול הגיליון
- [ ] כתוב לפי התבנית
- [ ] הצג החלטה אחת שנדרשת
```
הוסיפו **לולאת בדיקה**: "אם בדיקה נכשלה, חזור לשלב 3."

### דוגמה: `SKILL.md`
```markdown
---
name: preparing-weekly-reports
description: Prepares the weekly management report from the team sheet. Use when the user asks for a weekly report, weekly summary, or status update for management.
---

# Weekly report

## תוצאה
עמוד אחד: שלושה הישגים, שלושה סיכונים, החלטה אחת שנדרשת. עברית, ללא מונחים מקצועיים.

## שלבים
1. קרא את הגיליון העדכני ב-[נתיב].
2. כל מספר בדוח חייב להופיע בגיליון. אם חסר, סמן [חסר] ושאל.
3. כתוב לפי התבנית ב-reference/template.md.
4. בדוגמה ב-reference/example.md מופיע פלט מושלם.

## אילוצים
- אל תמציא מספרים או שמות.
- אם יש יותר משלושה סיכונים, בחר את החשובים ופרט מדוע.
```

## 2. פיתוח Skill בשיטת Claude A / Claude B

השיטה היעילה ביותר לפי התיעוד: **אתם עובדים עם מופע אחד (A) שבונה את ה-Skill, ובודקים אותו עם מופע חדש (B)**.

1. **ללא Skill:** עברו משימה אמיתית עם Claude A. שימו לב אילו הוראות הוספתם שוב ושוב.
2. **זהו את הדפוס:** מה שמרתם ששווה לשימוש חוזר?
3. **בקשו מ-A:** "צור Skill שמשמר את הדפוס הזה. כלול את הכללים שהוספתי."
4. **קצרו:** "הסר הסברים ש-Claude כבר יודע."
5. **ארגנו:** "העבר את המבנה לקובץ reference נפרד."
6. **בדקו עם B:** שיחה חדשה עם ה-Skill, על משימה דומה אך שונה.
7. **שפרו לפי מה שראיתם:** חזרו ל-A עם ממצא מדויק: "B שכח לסנן חשבונות בדיקה."

### בדיקות (Evaluations)
**בנו לפחות שלוש בדיקות לפני שמרחיבים:**

| # | תרחיש | מה ייחשב הצלחה |
|---|---|---|
| 1 | הבקשה הנפוצה ביותר | כל מספר תואם למקור, מבנה לפי התבנית |
| 2 | חסר מידע | מסמן [חסר] ושואל, לא ממציא |
| 3 | ניסוח לא רגיל של הבקשה | ה-Skill נטען בכל זאת |

- בדקו על **כל המודלים שתשתמשו בהם**. מה שעובד למודל חזק עלול להצריך יותר פירוט למודל קל.
- **בדקו גם שה-Skill לא נטען כשלא צריך.**
- שיתוף עם עמיתים והקשבה לאיך הם משתמשים הוא בדיקה שאין לה תחליף.

### כשהעלאה נכשלת
הסיבות הנפוצות: גודל, שם תיקייה שלא תואם ל-`name`, קובץ `SKILL.md` חסר או בשם שגוי, תווים לא חוקיים בשם או בתיאור.

## 3. Plugins ופיזור בארגון

**Plugin** מאגד Skills, חיבורים ו-sub-agents לחבילה אחת. בעלי הארגון יכולים להפיץ אותם כ: מותקן כברירת מחדל, חובה, זמין, או מוסתר.

### שכבות הניהול של Skills
| שכבה | מה קורה | מי |
|---|---|---|
| פרטי | הועלה, אף אחד לא רואה | כל משתמש |
| שיתוף | עם אנשים (קבוצות ב-Enterprise). נמענים רואים בצפייה בלבד | מי שבנה, אחרי שבעלים הפעילו שיתוף |
| פרסום לארגון | נשלח לספרייה, לעיתים נדרש אישור | מי שבנה, ומאשר |
| הקצאה לכולם | מותקן לכל המשתמשים | בעלים |
| הקצאה לקבוצה | דרך Plugin שמוקצה לקבוצה (Enterprise) | בעלים |

**בלי אישור הבעלים אין כפתור "Share".** [להשלים: מי הבעלים אצלנו, ומה תהליך הפרסום]

### אבטחה
- Skill יכול להריץ קוד ולהתקין חבילות. הסיכונים הם prompt injection והדלפת נתונים.
- **התקינו רק ממקורות מהימנים, וקראו את הקבצים והתלויות**, גם אם הוא נשלח מעמית.
- בארגון עם סריקת Skills פעילה, כל Skill שהועלה נבדק לפני הרצה.
- בעלים יכולים לחסום יצירה והעלאה עצמית ולהקצות רק Skills מאושרים.

## 4. Cowork מתקדם

### הוראות
- **Global instructions** (הגדרות > Cowork): העדפות כלליות לכל משימה.
- **Folder instructions:** הוראות ספציפיות לתיקייה או ללקוח.
- כתבו אותן כתוצאה רצויה ואילוצים, לא כזהות.

### Sub-agents ועבודה מקבילה
Claude מפצל משימה לתת-משימות ומתאם ביניהן. כך אפשר, למשל, לבקש: "בדוק שלושה ספקים במקביל והחזר טבלת השוואה אחת." **כל תת-משימה צורכת מכסה.**

### משימות מתוזמנות
דוחות שבועיים, ניטור שינויים, הכנת סדר יום. **תנו לכל משימה מתוזמנת בעלים ובדיקה:** מי קורא את התוצאה ומה קורה אם היא שגויה.

### גבולות ומגבלות
- שיחות לא ניתנות לשיתוף. Artifacts בודדים כן.
- חלק מהיכולות דורשות Desktop פתוח, בהן גישה לקבצים מקומיים, דפדפן ושליטה במחשב.
- **הגדרות egress** (רשת) לא חלות על חיפוש ברשת, web fetch, חיבורי MCP ו-Claude in Chrome. הן נכנסות לתוקף בתחילת שיחה בלבד.
- **היסטוריה מקומית** נשמרת במחשב, מחוץ למדיניות השמירה המרכזית.
- בדפדפן המובנה יש חסימת אתרים בסיכון גבוה ובדיקה של כל פעולה, אך התנועה יוצאת מהמכשיר שלכם.
- פרויקטים הקשורים לתיקייה מקומית עובדים רק ב-Desktop.

## 6. Claude Code

כלי שעובד עם הקבצים והקוד שלכם: קורא, כותב, מריץ ובודק. לא רק למפתחים: אנליסטים בונים איתו אוטומציות לגיליונות וניקוי נתונים.

### העיקרון: ספרו על מה שהוא לא יכול לראות
Claude קורא את הקוד ומבין לבד את המבנה, את הסגנון ואת הבדיקות. **כתבו רק מה שאי אפשר לגלות מהקוד:**
- החלטה שהתקבלה בפגישה.
- תהליך פריסה שנמצא בראש של אדם אחד.
- משתנה סביבה שנדרש לבדיקות.

מבחן: "האם ימצא את זה בקריאת הקוד? והאם יטרח לחפש?" אם שתי התשובות כן, אל תכתבו.

### בקשה ספציפית
| במקום | נסו |
|---|---|
| "תתקן את באג ההתחברות" | "משתמשים מדווחים שההתחברות נכשלת אחרי פקיעת הסשן. בדוק את חידוש הטוקן ב-src/auth/, כתוב בדיקה שנכשלת ומשחזרת את הבעיה, ואז תקן" |
| "תוסיף ווידג'ט לוח שנה" | "לפי הדפוס ב-HotDogWidget.php, בנה ווידג'ט שמאפשר לבחור חודש ולדפדף בין שנים. בלי ספריות חדשות" |

- הקבצים: `@` ונתיב. תמונות: הדביקו צילום. פלט פקודה: העבירו דרך pipe.
- **"be ambitious"** עוזר כשרוצים גרסה מלאה, עם מקרי קצה, ולא את המינימום.
- **ראיינו אותי:** "אני רוצה להוסיף [פיצ'ר] אבל לא חשבתי עד הסוף. ראיין אותי עד שתוכל לכתוב spec, וכתוב אותו ל-SPEC.md." אחר כך שיחה חדשה שבונה מה-spec.

### תנו בדיקה להרצה (החשוב ביותר)
Claude עוצר כשהעבודה "נראית גמורה". בלי בדיקה שחוזרת עם עבר/נכשל, אתם הבדיקה. תנו לו משהו שהוא מריץ בעצמו: בדיקות, קוד יציאה של build, linter, סקריפט שמשווה פלט, או צילום מסך מול מוקאפ.

| רמת אכיפה | איך |
|---|---|
| בבקשה | "הרץ את בדיקות ה-auth אחרי, והמשך עד שהן עוברות" |
| כיעד | `/goal` מגדיר תנאי שמודל נפרד בודק אחרי כל תור |
| כאכיפה | Stop hook שמחזיר את Claude לעבודה עד שהבדיקה עוברת |
| ביקורת חיצונית | `/code-review` סוקר את ה-diff בתת-סוכן שלא ראה את השיחה |

**בקשו ראיות:** הפקודה שהורצה והפלט שלה. "כל הבדיקות עוברות" לבדו מעיד מעט. אחרי סיום אפשר להריץ `/verify`, שבונה ומריץ את האפליקציה ובודק את התוצאה.

**בקשת סקירה מול ה-spec:**
```text
השתמש בתת-סוכן לסקור את ה-diff מול SPEC.md. בדוק שכל דרישה ממומשת ושלמקרי הקצה יש בדיקות. דווח על פערים שמשפיעים על נכונות, ודלג על סגנון.
```
> אל תוותרו על "דלג על סגנון". סוקר שמתבקש למצוא בעיות תמיד ימצא משהו.

### CLAUDE.md קצר
נטען בכל שיחה, לכן כל שורה לוקחת ממנו תשומת לב. כללו רק:
- איך מאמתים עבודה (פקודות test, typecheck, lint).
- מקומות שהקוד מטעה בהם.
- החלטות שאינן בקוד.
- כל מה שתיקנתם פעמיים.

```markdown
# Commands
- Run one test file: pnpm vitest run path/to/file.test.ts
- Typecheck: pnpm tsc --noEmit

# Gotchas
- Integration tests need DATABASE_URL, see .env.example
```

- `/init` יוצר גרסה ראשונה, ועיקר העבודה הוא הסרת שורות. מומלץ להישאר מתחת ל-200 שורות.
- `/doctor` ו-`/doctor prompt-audit` מזהים הוראות מיותרות, מיושנות או סותרות.
- העדפות אישיות: `CLAUDE.local.md`.
- **אם Claude מתעלם משורה:** או שהקובץ ארוך מדי, או שזה כלל בלי חריגים ולכן מקומו ב-hook.
- כללים שרלוונטיים לחלק מהקוד: `.claude/rules/` עם `paths:`.

### Skills ב-Claude Code
תהליכי צוות נשמרים ב-`.claude/skills/<name>/SKILL.md`. לפעולה עם תוצאות לוואי (פריסה, שחרור): `disable-model-invocation: true`, ואז היא רצה רק כשאתם מקלידים אותה.

### חיבור כלים
- יש CLI (למשל `gh`)? זו הדרך הקלה.
- אין? MCP: `claude mcp add --transport http <name> <url>`.
- כבו שרתים שלא בשימוש (`/mcp`). הם מוסיפים הקשר גם כשלא משתמשים.

### הרשאות ובטיחות
- שיחות חדשות מתחילות ב-**auto mode**: מסווג בודק פעולות מסוכנות לפני הרצה.
- **כללים בלי חריגים:** הרשאות ו-sandbox ל-"קובץ שאסור לקרוא", ו-hooks ל-"שלב שחייב לקרות".
- הרשאות רחבות רק בסביבה מבודדת.

### עלות והקשר
- שיחה קצרה וממוקדת מנצחת שיחה ארוכה. התחילו חדשה כשמסיימים משימה.
- הקשר מתכווץ אוטומטית לפני שהוא מתמלא.
- sub-agents שומרים את השיחה הראשית ממוקדת, אבל צורכים מכסה משלהם.
- הרצת סשנים במקביל או לפי תזמון זמינה, בעלות מתאימה.

### מי מוסר את האחריות
Claude כותב מהר. **אתם קוראים כל diff** לפני שמשהו נכנס לפרודקשן.

## 7. ממשל ואבטחה: מה גם צוות ה-AI והשגרירים צריכים לדעת

| נושא | מה לדעת |
|---|---|
| **Prompt injection** | הסיכון לא אפסי, למרות אימון וסיווגים. הוראות בתוכן חיצוני יכולות להטעות. אל תפעילו פעולות אוטומטית על תוכן לא בדוק |
| **חיבורים** | כל חיבור הוא דלת. "Always allow" כבוי כברירת מחדל. חברו מינימום |
| **Cowork** | מופעל כברירת מחדל ב-Team ו-Enterprise. בעלים מנהלים סשנים בענן, דפדפן מובנה ואישור אוטומטי |
| **שמירת נתונים** | נתוני ענן נשמרים בחשבון המשתמש. היסטוריה מקומית לא כפופה למדיניות שמירה, ואין עדיין מחיקה מרכזית |
| **ביקורת** | Compliance API מתעד שיחות Cowork. OpenTelemetry מזרים אירועים ל-SIEM, ואינו תחליף ללוג ביקורת |
| **זיכרון** | ב-Enterprise בעלים יכולים לכבות אותו לכל הארגון, ואז כל נתוני הזיכרון נמחקים. בעלים לא רואים זיכרונות אישיים |
| **Skills** | סריקת Skills אפשרית. אפשרות לחסום יצירה עצמית ולהקצות רק מאושרים |
| **Claude Design** | כבוי כברירת מחדל ב-Enterprise |

**מה לעשות בפועל כשבונים לצוות:**
1. מינימום הרשאות בכל חיבור.
2. אישור ידני לכל פעולה שיוצאת מהארגון.
3. סקירת כל Skill לפני פרסום, על ידי אדם שלא כתב אותו.
4. מי הבעלים של כל משימה מתוזמנת.
5. נוהל דיווח: [ערוץ אבטחת מידע].

## 8. תרגול (חצי יום)

**תרגיל 1: Skill עם בדיקות.** בחרו תהליך חוזר בצוות. כתבו `SKILL.md`, שלוש בדיקות, והריצו אותן עם שיחה חדשה. **הצלחה:** ה-Skill נטען נכון בשני מתוך שלושת הניסוחים, וקיבל פלט תקין בכל השלושה.

**תרגיל 2: סקירת אבטחה.** קחו Skill של עמית וסקרו: קבצים, תלויות, גישה לרשת. **הצלחה:** מצאתם לפחות שאלה אחת שדורשת הבהרה.

**תרגיל 3: אוטומציה ב-Claude Code.** נקו נתונים מקובץ חוזר, עם בדיקה שהסכומים תואמים למקור. **הצלחה:** הבדיקה מאתרת שינוי שהוכנס בכוונה.

**תרגיל 4: משימה מתוזמנת.** הקימו משימה שבועית עם בעלים וקריטריון "מה נחשב שגוי". **הצלחה:** אדם אחר קרא את התוצאה, ובדק.
